# Kosmohack_sputniki

Проект для КосмоХакатона 2026, трек «Автономное управление спутниковой группировкой».

Делаем веб-сервис для оператора смены. Он раздаёт задания спутникам (передача данных на Землю, ретрансляция), следит за зарядом, температурой и калибровкой, пересчитывает план, когда приходят новые заявки, отказы или отмена сеансов связи, и сравнивает два варианта продолжения смены из одного состояния.

Бэкенд на FastAPI, планировщики свои (baseline и smart), фронтенд — интерфейс оператора одной страницей. Задеплоено на Render: **https://kosmohack-sputniki.onrender.com** (бесплатный тариф засыпает через 15 минут простоя, перед демонстрацией нужно зайти на сайт заранее, чтобы он проснулся).

## Что где лежит

- `model/` - расчётная библиотека организаторов (`resource_env.py`, `operations.py`), её не трогаем
- `data/` - сценарии P01-P04
- `docs/` - постановка задачи, критерии оценки и описание данных (PDF от организаторов)
- `examples/` - пример событий во время смены (`events_demo.json`)
- `planner/` - наши планировщики и всё, что считает результаты:
  - `baseline.py` - простое правило (по дедлайну, приоритету и цене), точка отсчёта
  - `smart.py` - планировщик с заглядыванием вперёд, подробнее ниже
  - `explain.py` - почему конкретное задание не выполнено, с доказательством числами
  - `stats.py` - загрузка группировки: сколько времени спутник работал, калибровался или простаивал, и почему
  - `run_compare.py` - прогоняет baseline и smart по всем сценариям и обеим целям, складывает таблицу в `results/comparison.md`
- `app/` - веб-сервис: `server.py` (FastAPI, все эндпоинты) и `static/` (интерфейс оператора)
- `tests/` - тесты (32 штуки, все зелёные)
- `results/` - сохранённые расчёты и таблица сравнения

## Как работает планировщик

`baseline.py` на каждом шаге просто берёт самое срочное и дорогое задание из доступных и отдаёт его свободному спутнику, ничего не считая заранее.

`smart.py` пытается быть умнее:

1. Для каждого открытого задания считает запас времени (slack) — сколько ещё шагов с подходящим окном связи у него останется до дедлайна, за вычетом самой работы. Если запас отрицательный, задание физически не успеть никаким планировщиком, и ресурсы на него не тратятся.
2. Сортирует задания под выбранную цель (приоритетное обслуживание или выручка) и раздаёт жадно, проверяя лимит наземной связи (не больше 2 downlink за шаг) и физическую возможность выполнения.
3. Перед тем как занять спутник неглавной работой, грубо прикидывает по энергии, не помешает ли это ближайшему приоритетному заданию этого же спутника.
4. Если спутник простаивает, а калибровка истечёт раньше следующего окна связи — калибрует заранее, но не отбирает шаг у задания, которому он нужен прямо сейчас.

Планировщик не знает о будущих событиях (новые задания, отказы спутников, отмена сеансов) — только о тех, что уже произошли, как и требует постановка задачи.

Когда задание не выполнено, `explain.py` раскладывает причину по шагам и говорит главную: спутник был занят более важным заданием, мешала калибровка, не хватало энергии до резерва, мешал тепловой лимит, не было места в лимите наземной связи, спутник был в отказе, или планировщик сам отказался, потому что запас по времени уже кончился. `stats.py` отдельно показывает `contact_utilization` — какая доля шагов с доступным окном связи реально ушла на задания, а не простояла: если она низкая, узкое место не в ресурсах, а в окнах связи; если высокая — упираемся в реальную нехватку ресурсов.

## Результаты

Полная таблица по всем сценариям, обеим целям и обоим алгоритмам — в [`results/comparison.md`](results/comparison.md) (генерится командой `python3 planner/run_compare.py`). Коротко:

- **P01** (16 аппаратов, вводный): 11/18 заданий выполнено что baseline, что smart — и это же потолок по окнам связи, дальше физически никак не разогнаться.
- **P02/P03**: smart выходит на потолок по приоритетным заданиям (315/315), baseline берёт только 296–304. На P02 44 из 50 упущенных заданий физически невозможны по окнам связи — это не проигрыш алгоритма.
- **P04** (8120 заданий, перегрузка группировки): smart-priority делает 5772/8120 заданий и укладывает в срок 1664/1692 критичных (у baseline — 1230). Smart-revenue делает 6119/8120 и приносит $176k выручки против $125k у baseline. `contact_utilization` тут около 87% (у P02/P03 — около 15%), то есть на P04 упираемся именно в нехватку ресурсов группировки, а не в слабость планировщика; основная причина потерь — спутник занят более важным заданием.

## API

Бэкенд поднимает сессию смены в памяти и крутит выбранный планировщик по шагам:

- `GET /api/scenarios` - список сценариев
- `POST /api/scenarios/custom` - сохранить сценарий с правками (`overrides`) до запуска, получить его id
- `POST /api/sessions` - создать сессию (сценарий, цель, алгоритм)
- `POST /api/sessions/{id}/step` - продвинуть на n шагов
- `POST /api/sessions/{id}/run` - продвинуть до конкретного шага
- `POST /api/sessions/{id}/event` - применить событие (новые задания, отказ спутника, отмена сеанса)
- `POST /api/sessions/{id}/goal` - сменить цель на лету
- `POST /api/sessions/{id}/compare` - сравнить два варианта продолжения смены из текущего состояния
- `GET /api/sessions/{id}/explain` и `/explain/{job_id}` - почему задания не выполнены
- `GET /api/sessions/{id}/stats` - загрузка группировки
- `GET /api/sessions/{id}/scenario` и `/result` - исходный сценарий сессии и итог смены

## Запуск

Нужен Python 3.10 или новее.

```bash
git clone https://github.com/Grafitiks/Kosmohack_sputniki.git
cd Kosmohack_sputniki
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python3 -m pytest
```

Поднять сервис локально (интерфейс оператора откроется на `http://localhost:8000/`):

```bash
python3 app/server.py
```

## Запуск в контейнере

Есть `Dockerfile` — сессии сервис держит в памяти, ничего на диск не пишет и не читает localhost, так что образ можно катить на любой хостинг как есть.

```bash
docker build -t kosmohack-sputniki .
docker run -p 8000:8000 kosmohack-sputniki
```

Порт слушает `$PORT`, если хостинг его задаёт (иначе 8000 по умолчанию). Именно так задеплоено на Render.

## Как воспроизвести конкретный прогон

Каждый сохранённый прогон можно проверить заново:

```bash
python3 model/operations.py --result results/файл.json --output replay.json
```

Полные прогоны с trace (с ними и проверяется воспроизводимость) в репозитории не лежат — они тяжёлые, по несколько десятков мегабайт на сценарий. Получить их можно командой `python3 planner/run_compare.py --save-runs` (лягут в `results/runs/`, в `.gitignore`).
